## 1. 先认清你们在做一件什么事

你们不是"用 AI 写游戏"，你们是**用 AI 当实现团队，自己当规则制定者、验收员、手感总监**。这两件事的差别决定了整套工作流长什么样。

这套工作流只在一件事成立时有效：

> **AI 的每一份改动，都有人读过 diff、跑过命令、亲手玩过。**

[AGENTS.md](../AGENTS.md) 第 12 节已经把边界写死了，请记住这个分工：

| | 谁能保证 |
|---|---|
| **AI 能保证** | 跑过的测试全绿、行为符合验收标准、改动范围受控 |
| **AI 不能保证** | 架构是否合理、手感是否好玩、以后会不会难扩展、有没有想不到的边界情况 |

还有一个必须建立的心理预期：**AI 越快，你们的验收时间越长。** [00-学习路线.md](00-学习路线.md) 第 5.1 节给的实测比例是——AI 写一个敌人 20 分钟，验收加调手感 2 小时。所以这套工作流的重心从来不在"怎么让 AI 写得更多"，而在"怎么在它写完的 30 分钟内判断出它有没有搞坏东西"。

## 2. 角色分工

### 2.1 四个角色

| 角色 | 主要职责 | 独占的目录/文件 | 在每个功能里做什么 |
|---|---|---|---|
| **① 架构 + 主 AI 操作者** | 和 AI 对话、跑命令、管装配顺序与依赖注入 | `game/scripts/core/`、`game/project.godot`（改前先全员确认） | 按四段式派活 → 贴回完整输出 → 判断改动是否越过架构边界 |
| **② 战斗 + 手感负责人** | 帧数据、伤害公式、打击感数值 | `game/scripts/combat/`、`game/data/attacks.json` | 写"帧数级"的验收用例；用 `feel` / `hitstop` / `shake` 调参；对改动后的手感签字 |
| **③ 角色 + 关卡负责人** | 玩家、敌人、房间与刷怪数据 | `game/scripts/player/`、`game/scripts/world/`、`game/data/rooms.json`、`game/data/enemies.json` | 写"角色行为级"的验收用例；用 `next` / `tp` / `attack` 做场景验证 |
| **④ 验收 + 审 diff 负责人** | **每一份 diff 的第一读者**、测试与文档、验收记录归档 | `game/tests/`、`docs/` | 按第 6 节清单审 diff → 跑命令 → 开窗口玩 → 填验收记录表 |

**这张表和 [AGENTS.md](../AGENTS.md) 第 2 节的"文件所有权"是同一件事**，只是换了个角度看：那边说的是"哪个目录谁负责"，这边说的是"每个人在每个功能里扮演什么角色"。

两条补充规则：

- **`game/scenes/*.tscn` 同一时间只能有一个人在改。** 场景文件冲突极难解决，而且节点改名会让代码里的 `$Hurtbox`、`$Camera2D` 直接失效。要改场景，先在群里说一句，改完必须跑冒烟测试。
- **`game/tests/` 是所有人共用的**，规则只有一条：**只许增加，不许删除或弱化已有断言**。某个断言过不了，说明代码错了，不是测试错了。

### 2.2 只有 3 个人 / 2 个人怎么办

| 人数 | 怎么兼 |
|---|---|
| **4 人** | 按上表一人一岗 |
| **3 人** | ① 和 ④ 由同一人兼（他最懂架构，也最该审 diff）；②③ 不变 |
| **2 人** | A：架构 + 战斗手感 + 和 AI 对话；B：**专职读 diff 和验收**（角色/关卡的文件也归 B 审）。B 不是"打杂"，B 是这个项目能不能活过第 4 个月的关键岗位 |

人数再少也要守住一条：**写的人和审的人不能是同一轮对话**。你自己让 AI 写完、自己点通过，等于没审。

### 2.3 铁律：必须至少有一个人读每一份 AI 的 diff

不读 diff 会发生什么？下面是四种真实会出现的后果（前三种是典型模式，第四种已经在冒烟测试里被固化成断言了）：

1. **AI 顺手重构，悄悄改掉别的系统。** 它被要求改 `enemy.gd`，却"顺便"整理了 `hurtbox.gd` 里无敌帧递减的顺序。单元测试全绿——因为测试断言的是"无敌期间免疫伤害"这种区间性质，而不是"无敌帧恰好递减 30 次"。
2. **手感数值被改掉，而测试永远是绿的。** 它觉得 `light_1` 的 6 帧起手"太慢"，改成 4 帧。测试不看手感，只看到帧数据合法，全部通过。等你们周末打起来才发现轻击变得轻飘飘。
3. **测试断言被弱化。** 某条断言过不了，它把 `assert_eq(hp, 92)` 改成 `assert_le(hp, 100)`。测试绿了，功能坏了，而且**你们失去了唯一能发现这个问题的工具**。
4. **`source_team` 漏设。** 这是本骨架真实抓到的 bug：敌人在 `_ready()` 里忘了设 `hitbox.source_team = "enemy"`（默认值是 `"player"`），结果是**山贼打不到玩家，却互相误伤，还把训练木桩砍死**。代码审查完全看不出来——那一行只是"少了一行"，没人会注意到；是冒烟测试跑起来才发现的。

**另外两个真实抓到过的 bug，也说明了为什么"读 diff"和"跑起来"缺一不可：**

- **`hitbox.end_swing()` 在 `area_entered` 信号回调里直接写 `monitoring = false`**，Godot 报 `Function blocked during in/out signal` 并**静默失败**，判定盒一直开着，敌人死了还在挨打。这个坑连读 diff 都不一定看得出来，必须靠"真的把游戏跑起来 + 断言敌人掉血次数"。
- **换房间时玩家重新实例化，新玩家的 `replay_source` 是 null**，导致换房之后自动测试和回放都失去输入（角色站着不动）。这也是冒烟测试发现的。

**结论**：读 diff 能挡住"改坏了别的代码"，跑冒烟测试能挡住"接线接错了"。这两件事都不能省。

## 3. 一天 / 一周的工作循环

### 3.1 一个功能从"想做"到"合并"的完整流程

| # | 步骤 | 谁做 | 产出 |
|---|---|---|---|
| 0 | **先 commit 一次**（哪怕只是 `wip: 准备加冲刺无敌`） | ① | 一个能回退的基线 |
| 1 | **定需求 → 当场写成验收用例** | 提出人 + ④ | issue 里的一张"操作 → 期望"表（模板见 [03-验收清单.md](03-验收清单.md) 第 4 节） |
| 2 | **拆任务、查所有权** | ① | 一份 ≤ 3 个文件的改动清单；确认没人同时在动 `scenes/` |
| 3 | **派活**（四段式） | ① | 一段提示词 |
| 4 | **AI 自测并回报** | AI | 改动清单 + 三条命令的完整输出 |
| 5 | **审 diff** | ④ | 通过 / 打回（按第 6 节清单） |
| 6 | **人工核实** | ② 或 ③ | 跑命令看退出码 → 开窗口玩 → 用调试台对验收用例 → 录屏 |
| 7 | **合并** | ① | 一个 commit / 一个 PR，只做这一件事 |
| 8 | **记一笔** | ④ | 验收记录表贴进 PR；失败项开成新 issue |

第 1 步有个硬规定：**没写验收用例的功能不算做完，只算"写完了"**（[00-学习路线.md](00-学习路线.md) 误区 2）。用例必须在 AI 动手**之前**写，否则你会不自觉地按它的实现来验收——那等于没验。

### 3.2 一周的固定节奏

直接沿用 [00-学习路线.md](00-学习路线.md) 第 5.2 节的排法，这里只补一句**本项目专属的改动**：

> **把"读 diff"排成一个固定时段，而不是"有空就看"。** 建议放在周二、周三晚上"让 AI 写"之后的同一时段（各 30 分钟），由 ④ 主持，① 在场解释。理由很实际：不排进日程的事，在 2-4 人的业余团队里 100% 会消失。

### 3.3 四条时间纪律

前三条来自 [00-学习路线.md](00-学习路线.md) 第 5.3 节，第四条是本项目加的：

1. **每天不超过 1 小时连续"读 AI 代码"。** 超过 1 小时注意力会掉，你会开始"看不懂也点通过"。
2. **周五之前必须有一个能跑起来的版本。** 永远不要把"跑不起来"的状态留到周末。
3. **每周至少留 2 小时纯粹玩自己的游戏**，不做任何开发。
4. **每周至少完整跑一次 `run_tests.gd` + `smoke_run.tscn`，把结果数字贴进周报。** 数字本身就是信号：`225 → 228` 是好事；`225 → 217` 说明有人删了测试，立刻停下查；冒烟 `96 → 95` 同理。

## 4. 怎么给 AI 派活

### 4.1 模板在别处，纪律在这里

**通用模板（上下文 / 目标 / 约束 / 验收标准）在 [00-学习路线.md](00-学习路线.md) 第 3 节，四段缺一不可。** 缺哪一段，AI 就会在哪一段自由发挥——而自由发挥的部分通常不是你要的。

在这个项目里，无论任务多小，下面三句话**必须写进提示词**：

```text
- 动手前先读 AGENTS.md，以及 <文件A>、<文件B>、<它的测试文件>。
- 只允许修改 <文件A>、<文件B>（最多 3 个文件）。其他文件一律不动，包括 tests/ 里的已有断言。
- 改完自己跑下面三条命令，把**完整输出**贴给我，不要只说"通过了"：
    .tooling\Godot_v4.7.2-stable_win64_console.exe --headless --path game --import
    .tooling\Godot_v4.7.2-stable_win64_console.exe --headless --path game --script res://tests/run_tests.gd
    .tooling\Godot_v4.7.2-stable_win64_console.exe --headless --path game res://tests/smoke_run.tscn
```

（[AGENTS.md](../AGENTS.md) 第 1 节给的是 bash 写法的同一组命令，意思完全一样。本文统一用 Windows PowerShell 能直接粘的写法。）

### 4.2 实例 A：数据 + 手感类任务（2 个文件）

> 下面两个实例都是**还没做的任务**，用来说明"这个项目里的一份好提示词长什么样"，不是现状描述。

```markdown
## 上下文
- 项目：Godot 4.7.2 + GDScript 的横版武侠肉鸽（参考《死亡细胞》），骨架已跑通。
- 相关文件：
  - game/data/attacks.json —— 帧数据表，所有招式数值都在这里
  - game/tests/test_attack_table.gd —— 校验帧数据合法性（含 cancel_from 的合法区间、
    cancel_into 指向的招式必须真实存在）
  - AGENTS.md 第 5 节「帧数据约定」—— 帧编号方式和字段约束
- 当前行为：
  - light_3（轻击三段）是 8/4/18 = 30 帧，cancel_from = -1、cancel_into = []，打完才能动
  - heavy_1（重击·力劈）是 14/5/22 = 41 帧，目前没有任何招式能接进它，等于废招
- 动手前请先读上面三个文件。

## 目标
让轻击三段在收招后半段能取消接重击，只改数据、不改逻辑：
1. light_3 的 cancel_from 改成 20（合法区间是 startup+1=9 ~ total_frames=30）
2. light_3 的 cancel_into 改成 ["heavy_1"]
3. 其余任何数值一律不动

## 约束
- 只允许修改：game/data/attacks.json、game/tests/test_attack_table.gd
- 不许改任何 .gd 逻辑文件（player_fsm.gd 的取消窗口逻辑已经写好了，不要碰）
- 不许改 light_1 / light_2 / heavy_1 / enemy_swipe 的任何字段
- JSON 注释只能用 `_` 开头的键，不要用 // 或 #
- 不要顺手重构 attacks.json 的字段顺序，不要改缩进风格

## 验收标准
1. 第 19 帧按 J 不接重击，第 20 帧按 J 接上 heavy_1
   （在 test_attack_table.gd 里断言 light_3.can_cancel_at(19) == false、can_cancel_at(20) == true）
2. heavy_1 仍然不可取消：对任意帧 can_cancel_at() 都是 false（反向用例）
3. light_3 打完（frame >= 30）之后按 J 不再接任何招（反向用例）
4. 我在游戏里用 `attacks` 命令能看到 light_3 显示"第 20 帧起可接 heavy_1"
5. 跑 --import、run_tests.gd、smoke_run.tscn，贴出完整输出
6. 列出你改的每一处和原因
```

### 4.3 实例 B：新建纯逻辑类任务（3 个文件）

```markdown
## 上下文
- 相关文件：
  - game/scripts/world/enemy.gd —— 山贼/木桩的节点层
  - game/scripts/player/player_fsm.gd —— **接口形状照抄它**：extends RefCounted，
    tick(...) 返回 Dictionary，不引用场景树、不引用 EventBus
  - game/data/enemies.json —— bandit 的数值：move_speed 72、detect_range 260、
    attack_id "enemy_swipe"、attack_interval_frames 96
  - game/tests/test_player_fsm.gd —— 单元测试的写法参考
- 当前行为：山贼的决策写在 enemy.gd 的 _tick_walker() 里：距离 > 260 不动；
  否则朝玩家走（速度 72）；距离 < 34 且攻击冷却结束时出招 enemy_swipe（38 帧），
  之后冷却 96 帧。因为写在 Node 里，**没法单元测试**——"冷却期间会不会连出招"
  这种规则现在只能靠肉眼。
- 动手前请先读上面四个文件。

## 目标
把山贼的"察觉 → 靠近 → 进入 34 像素出招 → 冷却 96 帧"这段决策搬进新的纯逻辑类，
行为必须和现在**完全一致**：
1. 新建 game/scripts/world/enemy_fsm.gd，`extends RefCounted`，接口：
   func tick(distance_to_player: float, player_alive: bool) -> Dictionary
   返回 { "move_axis": -1/0/1, "attack_requested": bool }
2. enemy.gd 只负责读状态机结果、设 velocity、开关判定盒；_tick_walker 里的
   距离判断和冷却计数全部删掉
3. 数值（260 / 34 / 96 / 72）不许硬编码在 enemy_fsm.gd 里，通过构造参数传入

## 约束
- 只允许：新建 enemy_fsm.gd、修改 enemy.gd、新建 tests/test_enemy_fsm.gd
- 不许改 data/enemies.json 里的任何数值（这次只搬代码，不动手感）
- 不许改 hitbox.gd / hurtbox.gd / combat_director.gd，不许改任何 .tscn
- 不许用全局随机函数；不许用 await；不许在 _process 里做判定
- 新建 .gd 之后必须跑 --import

## 验收标准
1. 距离 300（> 260）时 move_axis == 0 且 attack_requested == false
2. 距离 100 时 move_axis 指向玩家
3. 距离 34 以内且冷却结束时 attack_requested == true；
   紧接着的 96 帧内不再为 true（反向用例）
4. player_alive == false 时不移动、不出招（反向用例）
5. 行为不变：改前改后，同一房间同一种子下山贼的出招时机一致（用 `dump` 对比或录屏逐帧对比）
6. 冒烟测试里"敌人真的打中了玩家"这一项仍然通过（说明 enemy→player 链路没被搬坏）
7. 贴出 --import、run_tests.gd、smoke_run.tscn 的完整输出
```

### 4.4 派活时最容易漏的三句话

| 漏掉的话 | 会发生的后果 |
|---|---|
| "不许动已有测试断言" | 它会把过不了的断言改松，你会以为功能好了 |
| "不许顺手重构无关代码" | diff 里出现大片删除线，你根本分不清哪一行是真正要改的 |
| "不许改 .tscn / project.godot" | 场景和项目配置被悄悄改动，冒烟测试可能才发现，也可能发现不了 |

## 5. 改动大小的纪律

### 5.1 硬上限

- **一次改动不超过 3 个文件。**（[AGENTS.md](../AGENTS.md) 第 7 节禁止行为第 9 条）
- **一个 PR / 一个分支只做一件事。**

> 注意：[00-学习路线.md](00-学习路线.md) 误区 3 里写的是"超过 200 行或 5 个文件，验收能力归零"——那是给初学者的更宽松的提醒。**本项目以 AGENTS.md 的 3 个文件为准**，两者不冲突，只是严的那条生效。

### 5.2 为什么是 3 个

| 理由 | 具体到你们的处境 |
|---|---|
| **审查带宽** | 你们每天只有 1 小时能有效读代码（第 3.3 节纪律 1）。3 个文件的 diff 大约 15 分钟能读完，10 个文件读完你就已经"看不懂也点通过"了 |
| **回滚成本** | 一个 commit 一件事，出问题 `git revert` 一下两秒钟回到能跑的状态；一个 commit 混了 5 件事，你只能整段丢弃 |
| **定位成本** | 改 3 个文件时你记得住自己批过什么；改 30 个文件时，测试红了只能靠猜是哪一段 |

### 5.3 怎么把大需求拆开（这个项目的拆法）

"帮我实现完整的战斗系统，包括连招、格挡、弹反、处决、武器切换" → 拆成：

1. `light_3` 加取消接 `heavy_1`（数据，2 文件）
2. 把山贼 AI 抽成 `enemy_fsm.gd`（纯逻辑，3 文件）
3. 给山贼加受击硬直（`enemy.gd` + `game_config.gd`，2 文件）
4. 给山贼加受击白闪（`enemy.gd`，1 文件）
5. 加格挡：先写 `guard.gd`（纯逻辑）+ 测试（2 文件），**再接进节点层**（1 文件）

**判断标准**：如果你没法为这次改动写出一张"操作 → 期望"的验收表，说明它还是太大，继续拆。

## 6. 怎么读 diff

### 6.1 15 分钟流程

1. **先看文件数量**：`git status` / `git diff --stat`。超过 3 个文件，直接打回，不用往下看。
2. **再看有没有动 `game/tests/` 和 `game/scenes/`**。动了 `tests/` 就要逐行确认是"新增"还是"改松"；动了 `scenes/` 就要问是谁批准的。
3. **逐行看 `+` / `-`**，对着 6.2 的清单扫一遍。
4. **最后问 AI 三个问题**（它会答，但更重要是逼你自己想清楚）：
   - 这一行为什么必须改？
   - 为什么改在这个文件，而不是它原来的位置？
   - 如果这一行不改，会出什么问题？

### 6.2 必查清单

| 看到什么 | 为什么危险 | 怎么办 |
|---|---|---|
| **顺手重构**：改了不相关的行、重命名变量、调整函数顺序 | AGENTS.md 第 6.7 条明令禁止；它会把风险混进本次改动 | 要求只保留任务相关的行，其余回退 |
| **硬编码数值**：`if hp < 37`、`if frames > 12` | 手感数值必须集中在 `game_config.gd` / `data/*.json`（规矩 5） | 要求改成 `GameConfig.XXX` 或数据表字段 |
| **删掉不相关的行**（diff 里大片红色） | 最危险的一类：删掉的可能正是下一阶段要用的代码 | 逐行问"这行为什么要删"，恢复 |
| **调试垃圾**：`print("here")`、注释掉的大段旧代码、临时变量 | 提交前必须删干净（第 6.6 条） | 要求删掉，并要求它以后不留 |
| **改测试断言**（`tests/` 里出现 `-` 号） | 断言只许增加不许弱化（第 7 节禁止行为 2） | 立刻停下：断言过不了说明代码错了，不是测试错了 |
| **改 `.tscn` 场景文件** | 同一时间只能一个人改；节点改名会让 `$Hurtbox`、`$Camera2D` 直接失效 | 确认是谁批准的；改完必须跑冒烟测试 |
| **改 `project.godot` / `.gitignore` / `.gitattributes` / `*.uid`** | 前三者改错会让项目打不开或仓库状态混乱；`.uid` 必须提交但不要手改 | 一律先问人，问清楚再决定 |
| **新增 `addons/` 或任何第三方依赖** | 第 7 节禁止行为 1 | 直接拒绝 |
| **全局随机函数**：`randi()` `randf()` `randi_range()` `randf_range()` `randomize()` `shuffle()` | 用了种子就复现不了一局（规矩 4） | 要求改用 `DeterministicRng` 的 `next_int` / `next_float` / `next_float_range` |
| **在 `_process` 里做判定** | 判定必须在 `_physics_process`（固定 60 帧/秒） | 要求挪到 `_physics_process` |
| **用 `await` 写游戏逻辑** | 时序不可预测，测试无法复现 | 要求改成"每帧 tick 一次" |
| **信号回调里直接 `monitoring = false`** | Godot 报 `Function blocked during in/out signal` 且**静默失败**（陷阱 2） | 要求走 `call_deferred` + token 的写法（照抄 `hitbox.gd`） |
| **直接写 `hp = ...`** | 只有 `Hurtbox.receive_hit()` 能改血量（规矩 2） | 要求走受击盒入口 |
| **新增带攻击能力的角色，没写 `hitbox.source_team`** | 就是真实抓到过的那个 bug：敌人打不到玩家却互相误伤（规矩 3） | 要求在 `_ready()` 里显式声明阵营 |
| **Tab 缩进 / 变量和返回值缺类型标注 / 英文注释** | 代码风格硬性要求（第 6 节） | 要求改回 4 空格、补类型标注、中文注释 |
| **新增了 `.gd` 文件但输出里没有 `--import`** | 不跑 import，`class_name` 互相引用会解析失败（陷阱 4） | 要求补跑并把输出贴出来 |

### 6.3 三种"看起来没问题"的危险 diff

1. **全是删除线的 diff。** 它说"这些代码没被用到，我清理掉了"。但那些代码可能是下一阶段要用的钩子（比如 `hurtbox.gd` 的 `stagger_requested` 信号目前还没有消费方，删了就得重写）。
2. **全是新增文件的 diff。** 它没有改现有代码，而是另起了一套并行的实现。这会绕过现有架构——两套写法以后必然打架。
3. **只在 `tests/` 里改动的 diff。** 测试从红变绿了，但你不知道是"代码改对了"还是"断言改松了"。这类 diff 必须逐行看断言。

## 7. AI 说"我做完了"之后你该做什么

### 7.1 六步核实（一步都不要跳）

```powershell
cd D:\dream_start
$godot = ".tooling\Godot_v4.7.2-stable_win64_console.exe"

# ① 它到底改了哪些文件（超过 3 个直接打回）
git status
git diff --stat

# ② 三条命令，看退出码（0 = 通过，1 = 有失败）
& $godot --headless --path game --import
& $godot --headless --path game --script res://tests/run_tests.gd
& $godot --headless --path game res://tests/smoke_run.tscn
```

1. **看它改了什么**：文件数、目录、有没有动 `tests/` 和 `scenes/`。
2. **跑三条命令**：注意退出码。只改了一个文件、想快速查语法可以用 `--check-only --script res://scripts/player/player_fsm.gd`，但它**不能替代**上面两条完整检查。
3. **只读测试输出的最后三行**：单元测试认准 `测试套件 11 个   测试方法 225 个   断言 1407 条   失败 0 个` 和 `结果：全部通过 ✓`；冒烟测试认准 `检查项 96 个   失败 0 个` 和 `结果：冒烟测试全部通过 ✓`。
   **中间的 `ERROR:` / `WARNING:` 大多数是预期的**——单元测试会故意喂错误数据来验证容错分支（见 [AGENTS.md](../AGENTS.md) 陷阱 5，以及第 1 节列的预期错误清单）。不要试图"修掉"它们，也不要因为它们存在就判定失败。
4. **开窗口亲手玩一次**（`& $godot --path game`）：按 `J` 打三下、按 `L` 冲刺、按空格跳一下、按 `` ` `` 打开调试台。这一步是唯一能发现"画面/表现层坏了"的手段——`--headless` 看不见画面。
5. **用调试台对验收用例**：`seed 20240501` → `restart` → `next` → `tp` / `hp` / `attack` / `god`，然后用 `check`、`data light_1`、`dump`、`feel`、`save`、`replay` 逐条比对（完整清单见 [03-验收清单.md](03-验收清单.md) 第 5 节）。
6. **填验收记录表**（模板见 [03-验收清单.md](03-验收清单.md) 第 8 节），贴进 PR 或 issue。

### 7.2 什么叫"证据不足"

下面这些都不算证据，一律要求它重贴：

| 它说 | 为什么不算 |
|---|---|
| "测试通过了" | 没有输出，无法判断它跑的是哪条命令、什么时候跑的 |
| 只贴了最后一行 | 无法判断测试数量有没有减少（`225 → 217` 也是"全部通过"） |
| 贴的是改动**之前**的输出 | 看输出里的帧数/种子/测试数量对不对得上本次改动 |
| 没贴命令本身 | 你不知道它有没有加 `--path game`，也不知道它跑的是哪个脚本 |
| "冒烟测试跳过了一些检查" | 冒烟测试没有"跳过"这种状态，只有 ✓ / ✗ |

### 7.3 三种必须打回的情况

1. **文件数 > 3**，或者改了 `tests/` 里的已有断言。
2. **退出码非 0**，但它说"这是预期错误"。退出码为 1 就是有失败，没有例外。
3. **它改了任务里没提到的文件**（哪怕只改一行）。

## 8. AI 卡住 / 胡说的时候怎么办

### 8.1 五种策略，按顺序试

| 顺序 | 策略 | 具体怎么说 |
|---|---|---|
| 1 | **缩小范围** | "先不要管别的，只改 `player_fsm.gd` 里 `_tick_attack()` 这一个函数，其他文件一律不动。" |
| 2 | **贴完整报错 + 你的判断** | 用 [00-学习路线.md](00-学习路线.md) 第 3.3 节的 bug 模板（环境 / 复现步骤 / 期望 / 实际 / 频率 / 日志 / 录屏 / **我的初步判断**）。不要只贴最后一行报错。再加一步：在游戏里跑 `dump` 把当前局面导出成 JSON 一起贴给它 |
| 3 | **让它先复述需求** | "先别改代码。用 5 行说明你打算改哪几个文件、每处为什么、会不会动到 `hurtbox.gd`。" 它复述错了，说明需求没传达清楚；复述对了，再让它动手 |
| 4 | **换一个更小的任务** | "这次只做第一步：把 AI 的决策搬进 `enemy_fsm.gd`，行为完全不变，不顺手优化。" |
| 5 | **回退重来** | `git stash` 或 `git checkout -- .` 或 `git reset --hard <上一个能跑的 commit>`，然后换一段更清楚的提示词。**回退不丢人，在烂代码上继续打补丁才丢人** |

### 8.2 什么情况直接回退，不要继续对话

- 它**连续 2 次**改坏同一个地方（第 3 次大概率还是坏的）。
- 它开始"解释为什么你的需求不对"，而不是干活。
- 它改了你不允许改的文件。
- 你发现自己在反复说同一句话（"我说了不要动测试断言"）。

### 8.3 什么时候换工具 / 换人

- **额度用完**：按 [01-工具清单.md](01-工具清单.md) 第 2.3 节的备用方案换（Gemini CLI 免费额度 / 网页版手工搬运，注意缩进）。
- **同一个 bug 换 3 种说法都修不好**：停下来，由人去读那 20 行代码，说出自己的判断（[00-学习路线.md](00-学习路线.md) 误区 4）。**你会读代码，AI 的修复成功率会翻倍；你不会读，就只是在一遍遍抽奖。**

## 9. 版本控制纪律

### 9.1 当前状态（先看这一段）

**截至本文写作时，`D:\dream_start` 下还没有 `.git` 目录**——执行 `git status` 会报 `fatal: not a git repository`。所以下面这套是**开工前要定下来的约定**，不是既成事实。

第一次让 AI 改代码之前，先做三件事：

1. `git init`，确认 `.gitignore` 已经生效（它已经排除了 `game/.godot/` 和 `.tooling/`）。
2. 提交一个基线 commit，比如 `chore: 骨架跑通（225 单元测试 + 96 项冒烟检查全绿）`。
3. 确认 `git lfs install` 已经执行过（[01-工具清单.md](01-工具清单.md) 第 4.1 节：装了 LFS 不初始化等于没装）。

### 9.2 分支命名

对齐 [00-学习路线.md](00-学习路线.md) 阶段 0 的写法，一个分支只做一件事：

```bash
git checkout -b feat/轻击三段接重击      # 新功能
git checkout -b fix/换房丢重放数据源      # 修 bug
git checkout -b data/轻击一段顿帧4改5     # 只改数值
git checkout -b test/补敌人AI反向用例     # 只改测试
git checkout -b docs/验收清单            # 只改文档
git checkout -b chore/启用GitLFS         # 杂务
```

分支名用中文没关系——**团队都看得懂比"符合英文规范"重要**，但要短。

### 9.3 提交信息格式

沿用 [00-学习路线.md](00-学习路线.md) 里已经出现过的写法（`feat: 冲刺加入 6 帧无敌`、`chore: 启用 Git LFS 管理美术与音频`、`wip: 准备加冲刺无敌`）：

```text
<类型>: <一句话说清改了什么>

改了什么：light_3 的 cancel_from 12 → 20，cancel_into 加 heavy_1
为什么：轻击三段打完必须等满 30 帧，连招断在这里，手感是断的
怎么验证：run_tests.gd 退出码 0（225 个测试 / 1407 条断言 / 0 失败），
          smoke_run.tscn 退出码 0（96 项检查 / 0 失败）
```

类型用：`feat` / `fix` / `data` / `test` / `docs` / `chore` / `wip`。

**禁止**：`update`、`fix bug`、`改了一下`、`提交`。三个月后你只能靠这些字找回当时的决定。

### 9.4 绝对不能提交 / 必须提交

| 类别 | 具体 | 说明 |
|---|---|---|
| **绝对不能提交** | `.tooling/` | Godot 本体，已在 `.gitignore` 里。每人自己下一份，版本必须是 4.7.2 |
| | `game/.godot/` | Godot 自动生成的导入缓存，已在 `.gitignore` 里，**永远不要碰** |
| | `game/build/`、`game/export/`、`*.pck`、`*.zip` | 导出产物，已在 `.gitignore` 里 |
| | `*.log`、`*.tmp` | 已在 `.gitignore` 里 |
| | **重放文件** | 写在 `user://replays/`，Windows 上落在 `%APPDATA%\Godot\app_userdata\武侠肉鸽 · 可验证骨架\replays\`，**本来就不在仓库里**。要交给队友就直接发文件，**不要拷进仓库**——`.gitignore` 并没有排除它 |
| | 原始音频工程、几十 MB 的 `.psd` | 用 Git LFS 或放网盘（[01-工具清单.md](01-工具清单.md)） |
| **必须提交** | `game/data/*.json` | 帧数据、敌人、房间——这是项目的手感与关卡，改一次提交一次 |
| | `*.uid` | Godot 生成的脚本 UID，**必须提交，但不要手改** |
| | `.gitattributes` | 管 LFS 和换行符（LF），保证四人环境一致 |
| **改之前必须问人** | `game/project.godot`、`.gitignore`、`.gitattributes` | 改错会导致项目打不开或整个仓库的文件状态混乱（AGENTS.md 第 7 节） |

### 9.5 每次让 AI 动手之前先 commit

这是 [00-学习路线.md](00-学习路线.md) 误区 7 的原话，在这个项目里尤其重要：**AI 协作模式下代码变动速度是手写的 5-10 倍，没有 Git 就是在裸奔。**

流程固定成两句话：

- **动手前**：`git commit -m "wip: 准备改 enemy AI"`（哪怕什么都没改完，先占一个能回退的点）。
- **验收通过后**：再 commit 一次，写清楚改了什么、为什么、怎么验证的。

## 10. 诚实的风险说明

### 10.1 如果没有人读 diff，这个项目大概会在 2-4 个月内停摆

这不是危言耸听，把账算清楚你就明白了：

- **变更速率乘以未检查率。** AI 的改动速度是手写的 5-10 倍（[00-学习路线.md](00-学习路线.md) 误区 7）。按每天 1-2 小时、每周 2-3 个功能算，大约 60-120 次改动之后，未审的改动就会积累到"没人知道哪段代码是谁写的、为什么这么写"的程度。
- **测试只覆盖行为，不覆盖设计。** `run_tests.gd` 能告诉你"伤害公式没算错"，`smoke_run.tscn` 能告诉你"接线没接错"。它们**永远**不会告诉你"这个类的职责放错了""这个依赖注入顺序以后会出事"。
- **手感数值混在 diff 里被改掉时，测试永远是绿的。** 帧数据只要满足校验规则（`startup ≥ 1`、`cancel_into` 指向存在的招式），测试就全过。改坏的是体验，不是逻辑。
- **架构腐化是复利的。** [00-学习路线.md](00-学习路线.md) 阶段 2 那句话值得贴墙：**AI 的产出质量，上限由项目结构决定。** 结构乱了以后，你给 AI 的每一份提示词都在一个烂摊子上打补丁，错误率上升 → 你要审的 diff 更多 → 你更不想审 → 循环加速。
- **"停摆"不是"失败"。** 项目不会崩掉，它会**卡住**：还能跑，但没人敢改；每改一次就多一个 bug；你们开始绕过核心文件打补丁，最后连自己都不敢动 `player_fsm.gd`。这个状态会一直持续到有人放弃。

### 10.2 另外四个真实风险

| 风险 | 触发条件 | 缓解办法 |
|---|---|---|
| **测试全绿但没有测试价值** | AI 只测了它自己实现的那条路（"能打中就通过"） | 每个功能强制 2 条**反向用例**（"不该发生什么"），写进派活模板的验收标准里 |
| **手感被"功能完成度"挤掉** | 忙着加敌人加房间，没人调帧数据 | 每周六固定 2 小时手感时段（[00-学习路线.md](00-学习路线.md) 第 5.2 节）；[00-学习路线.md](00-学习路线.md) 误区 6 的标准：让没玩过的人玩 30 秒，他说"有点飘"就停下加功能 |
| **四个人都动 `scenes/`** | 谁都想"顺手加个节点" | 场景同一时间只有一个人能改，改之前先说、改完跑冒烟测试（[00-学习路线.md](00-学习路线.md) 误区 8） |
| **项目依赖一个 AI 操作员** | 他请假一周，项目停一周 | **至少两个人会跑那三条命令**、会看退出码。这不是备份，是最低冗余 |

### 10.3 这份工作流的适用边界

- 它保证**行为不退化**（靠 [03-验收清单.md](03-验收清单.md) 的四层验收手段）。
- 它**不保证游戏好玩**（靠每周 2 小时纯粹玩自己的游戏）。
- 它**不保证架构合理**（靠架构负责人在改动超过 3 个文件、或有人想改 `scripts/core/` 时喊停，并要求先说明理由）。
