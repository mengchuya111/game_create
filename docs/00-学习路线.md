## 1. 一句话结论

**在这个项目里，你不需要"学会写代码"，但必须"能读懂代码"。**

把这两件事分清楚，是整条学习路线的核心：

| | 不需要学 | 必须会 |
|---|---|---|
| 编程本身 | 不需要从零学算法、数据结构、设计模式，不需要能默写 GDScript 语法，不需要能手写一个状态机 | 必须能看懂 AI 写的 `.gd` 脚本在干什么：哪一行是移动、哪一行是扣血、哪一行是播动画 |
| 工程能力 | 不需要学编译原理、内存管理、网络编程、多线程 | 必须会用 Git 提交、开分支、合并；必须会看代码 diff；必须会在 Godot 里跑起来并复现 bug |
| 能力定位 | 你不是"程序员" | 你是**规则制定者 + 验收员 + 手感总监**，AI 是你的实现团队 |

**一句话的实操标准**：AI 给你 100 行脚本，你能指着其中一行说"这里判断错了，角色在受击时不应该还能触发闪避"——能做到这一点，你就达标了。做不到，说明你跳过了阶段 1 和阶段 2。

**为什么可以这样分工？** 因为我们选的这套技术栈天然适合 AI 协作：

- Godot 的场景文件 `.tscn`、资源文件 `.tres` 都是**纯文本**，AI 能直接读写，不像 Unity 的 `.unity` 场景那样容易冲突。
- Godot 支持 **`--headless` 命令行运行**，AI 可以自己跑测试脚本、自己看报错、自己改，形成闭环。
- GDScript 语法**接近 Python**，公开语料多，AI 写错的概率明显低于 C++ / C# 这类语言。

## 2. 分阶段学习路线

时间按 **每天 1-2 小时**估算。全职投入的话把天数除以 3 左右。

**重要**：阶段 0 和阶段 1 结束（大约第 3 周）就应该开始做**最小可玩原型**（一个能跑能跳能砍的方块人），学习和开发并行，不要等"全学完再开工"。

### 2.0 总览表

| 阶段 | 主题 | 目标一句话 | 耗时（每天 1-2h） | 达标自测 |
|---|---|---|---|---|
| 0 | 环境与版本控制 | 四个人能安全地共用一份代码 | 约 1 周（7-10 小时） | 能独立解决一次合并冲突，并写出一条 AI 能复现的 bug |
| 1 | 读懂 Godot / GDScript | 能看懂 AI 写的每个脚本在干什么 | 约 2 周（14-20 小时） | 能不看解释说出 200 行脚本里"哪一行管移动" |
| 2 | 读懂游戏架构 | 能看懂项目整体的骨架 | 约 2 周（14-20 小时） | 能画出"按下攻击键 → 敌人掉血"的完整数据流 |
| 3 | 验收能力 | 能判断"这个功能到底做对了没有" | 约 1 周（7-10 小时），之后长期 | 能写出 5 条可执行的验收用例，并给出代码 diff 的具体意见 |
| 4 | 手感调优 | 能说出"哪里不对"并给出数字 | 约 2 周（14-20 小时），之后贯穿全程 | 能独立调出一套"起手 8 帧、判定 4 帧、收招 12 帧"的攻击 |

### 阶段 0：环境与版本控制（约 1 周）

**目标**：四个人能安全地共用一份代码库，任何一个人搞坏了都能退回去。

#### 要掌握的具体知识点

| 知识点 | 具体要会做什么 | 大概耗时 |
|---|---|---|
| 安装与配置 | 装 Godot 4、Git、VS Code，能打开项目、能运行项目 | 1 小时 |
| Git 基础 | `git clone` / `status` / `add` / `commit` / `push` / `pull` | 2 小时 |
| 分支 | `git branch` / `checkout -b` / 知道"每人一个功能分支"的规矩 | 1 小时 |
| 合并与冲突 | `git merge`、看懂 `<<<<<<< HEAD` 冲突标记、手工选择保留哪一段 | 2 小时 |
| Git LFS | 知道美术/音频是二进制文件，必须用 LFS 管；会 `git lfs track "*.png"` | 1 小时 |
| 提 issue | 会在 GitHub 上开 issue，会用标签区分 `bug` / `feature` / `手感` | 0.5 小时 |
| 描述一个 bug | 能写出"环境 + 复现步骤 + 期望 + 实际 + 日志/录屏"五段式 | 0.5 小时 |

#### 具体操作要点

**Git 最小工作流（记住这 6 条命令就够用 90% 的时间）**

```bash
git clone <仓库地址>              # 第一次：把项目拿下来
git checkout -b feat/冲刺闪避      # 开一个功能分支，名字写清楚在做什么
git status                        # 随时看：我改了哪些文件
git add . && git commit -m "feat: 冲刺加入 6 帧无敌"   # 存一个档
git push                          # 推到 GitHub
git checkout main && git pull      # 回到主干并拉最新
```

**冲突长什么样（一定要亲手制造一次）**

```text
<<<<<<< HEAD
var dash_speed := 400.0
=======
var dash_speed := 520.0
>>>>>>> feat/冲刺闪避
```

处理方式只有三步：删掉 `<<<<<<<`、`=======`、`>>>>>>>` 这三行标记，把中间留下的内容改成你真正想要的那一行，然后 `git add` + `git commit`。**不要怕冲突，怕的是不敢看。**

**Godot 项目的 `.gitignore`（直接复制）**

```gitignore
# Godot 4 自动生成的导入缓存，绝对不能提交
.godot/
# 导出产物
export/
build/
# 系统垃圾
.DS_Store
Thumbs.db
```

**Git LFS 要管的文件类型**

```bash
git lfs install
git lfs track "*.png" "*.aseprite" "*.psd" "*.wav" "*.ogg" "*.mp3" "*.ttf"
git add .gitattributes
git commit -m "chore: 启用 Git LFS 管理美术与音频"
```

> 注意：GitHub 免费账号的 LFS 额度是 **1 GB 存储 + 每月 1 GB 流量**（截至 2026-10 的公开政策，请以 GitHub 官网为准）。一个 2D 像素游戏的美术量通常够用；如果不够，把大文件放到网盘，仓库里只留压缩后的版本。

#### 达标自测标准

- [ ] 我能独立完成：改一个变量 → commit → push → 队友 pull 后能看到我的改动。
- [ ] 队友和我同时改同一个文件，我能独立解决冲突并解释我为什么保留这一段。
- [ ] 我能不看模板，写出一条合格的 bug issue（含复现步骤），队友照着我写的步骤能 100% 复现。

### 阶段 1：读懂 Godot / GDScript（约 2 周）

**目标**：AI 给你一个 200 行的脚本，你能说出"这段在管移动、这段在管受击、这段每帧都在跑"。

**这一阶段只要求"读"，不要求"写"。** 你的练习方式是：让 AI 写，然后你逐行加中文注释。

#### 要掌握的具体知识点

| 知识点 | 一句话解释 | 大概耗时 |
|---|---|---|
| 节点树（Node Tree） | Godot 里所有东西都是节点，节点套节点组成一棵树。`Player` 下面挂着 `Sprite2D`、`CollisionShape2D`、`AnimationPlayer` | 2 小时 |
| 场景（Scene / `.tscn`） | 一个可复用的节点树存成文件就是场景。`Player.tscn` 可以被 `Level1.tscn` 引用多次 | 2 小时 |
| 脚本挂载 | 脚本（`.gd`）必须挂在某个节点上才会运行；脚本里的 `self` 就是这个节点 | 1 小时 |
| 变量与函数 | `var speed := 200.0` 是变量，`func move():` 是函数。`:=` 表示让 Godot 自己推断类型 | 2 小时 |
| `_process` / `_physics_process` | 前者每渲染帧跑一次（画面上用），后者固定每秒 60 次跑（物理、移动、判定用）。**判定逻辑必须写在 `_physics_process`** | 2 小时 |
| 信号 signal | 节点之间的广播机制。`died` 是一个信号，`.emit()` 是发广播，`.connect(...)` 是订阅 | 3 小时 |
| 节点路径 `$Node` | `$Sprite2D` 就是"取我下面那个叫 Sprite2D 的子节点"，等价于 `get_node("Sprite2D")` | 1 小时 |
| `@export` | 让变量出现在 Godot 右侧属性面板里，不用改代码就能调数值。**手感调优主要靠它** | 1 小时 |
| `@onready` | "等节点树准备好了再取这个引用"，写 `@onready var sprite := $Sprite2D` 是标准写法 | 1 小时 |
| 常用节点类型 | `CharacterBody2D`（会移动的角色）、`Area2D`（判定区域）、`AnimationPlayer`、`Timer`、`Camera2D`、`TileMapLayer`（Godot 4.3+ 的瓦片地图） | 3 小时 |

#### 一段"你要能读懂"的样板代码

下面这段就是本项目角色移动的核心，读不懂就不要进阶段 2：

```gdscript
extends CharacterBody2D
# ↑ 这行说明：这个脚本挂在一个 CharacterBody2D 节点上，所以能用 velocity / move_and_slide()

@export var max_speed: float = 220.0      # ← 出现在右侧面板，我可以直接在编辑器里调
@export var acceleration: float = 1800.0  # ← 手感调优的旋钮，不用碰代码

@onready var sprite: Sprite2D = $Sprite2D # ← 等节点树就绪后，抓住子节点 Sprite2D

var facing: int = 1                       # ← 1 朝右，-1 朝左

func _physics_process(delta: float) -> void:
    # delta 是"距离上一次物理帧过了多少秒"。所有"随时间变化"的计算都要乘它。
    var direction := Input.get_axis("move_left", "move_right")   # 得到 -1 / 0 / 1

    if direction != 0:
        facing = signi(direction)                                 # 记住朝向
        velocity.x = move_toward(velocity.x, direction * max_speed, acceleration * delta)
    else:
        velocity.x = move_toward(velocity.x, 0.0, acceleration * delta)  # 松手减速

    sprite.flip_h = facing < 0        # 朝左时水平翻转贴图
    move_and_slide()                  # 真正让角色动起来（由 Godot 引擎处理碰撞）
```

**你要能从这段代码里回答的问题**：

1. 改哪个数字能让角色跑得更快？→ `max_speed`（在编辑器面板里就能改）
2. 这段代码每秒跑几次？→ 默认 60 次（`_physics_process`），改 `项目设置 → 物理 → 每秒物理帧数` 可调
3. 为什么松手会滑一下而不是立刻停？→ `move_toward` 是渐变减速，`acceleration` 越大滑得越短
4. 如果我把 `move_and_slide()` 删掉会怎样？→ 角色数值变了但画面不动

#### 达标自测标准

- [ ] 我能对着任意一个 AI 生成的脚本，用中文给**每一行**加注释，且注释是对的。
- [ ] 我能指出"这段逻辑为什么必须放在 `_physics_process` 而不是 `_process`"。
- [ ] 我能在 Godot 编辑器里新建一个场景，把 AI 写的脚本挂上去，让它跑起来不报错。
- [ ] 我能解释 signal 的作用：为什么敌人死了要 `emit()` 而不是直接去改 UI 的文字。
- [ ] 我能说出 `@export` 和普通 `var` 的区别，并知道**哪些数值应该做成 `@export`**（答案：所有手感相关的数值）。

### 阶段 2：读懂游戏架构（约 2 周）

**目标**：能画出"按下攻击键 → 敌人掉血 → 屏幕震动 → 音效播放"这条完整链路，并知道每一环在哪个文件里。

**为什么初学者也要学这个？** 因为不学，你就只能让 AI 一个文件一个文件地改，改到第 20 个功能时整个项目会变成一团乱麻，AI 也开始胡编——**AI 的产出质量，上限由项目结构决定。**

#### 要掌握的具体知识点

| 知识点 | 一句话解释 | 大概耗时 |
|---|---|---|
| 状态机（State Machine） | 把角色行为拆成互斥的状态：`Idle / Run / Jump / Attack / Hurt / Dash / Dead`。同一时刻只能在一个状态里，切换由明确的规则触发 | 4 小时 |
| 数据驱动 / 配置表 | 招式伤害、判定帧数、敌人血量、每层怪物数量**不写在代码里**，写在 `data/*.json` 里，改数值不用改代码 | 3 小时 |
| 事件总线（Event Bus） | 用一个全局单例（Autoload）做"广播站"，任何系统都能发/收事件，避免模块之间互相硬引用 | 3 小时 |
| **纯逻辑类（`RefCounted`）** | **本项目的核心架构决策**：算伤害、跑状态机、生成房间的代码**不继承 `Node`**，因此不需要场景树就能跑，也就能被单元测试直接调用 | 4 小时 |
| 场景组合与分层 | 分清 `player.tscn`（角色本身）、`main.tscn`（总入口）的职责边界 | 2 小时 |
| 碰撞层与遮罩 | `Layer` 是"我是什么"，`Mask` 是"我关心谁"。玩家攻击盒只关心敌人受击盒 | 2 小时 |

#### 最重要的一条架构规矩：**纯逻辑类不继承 `Node`**

这是整个项目里对"AI 协作"影响最大的一条设计，务必理解。

看 `player_fsm.gd` 的开头：

```gdscript
class_name PlayerFsm
extends RefCounted          # ← 不是 Node！
```

它**完全不知道场景树的存在**：没有 `_ready`，没有 `_physics_process`，没有 `get_node`。你给它一帧输入和一个"是否站在地上"的布尔值，它就返回"这一帧该处于什么状态、判定盒要不要开"。

为什么这样做？因为只有这样才能写**单元测试**：

```gdscript
var fsm := PlayerFsm.new()
var result := fsm.tick(PlayerInputFrame.with_attack(), true, 0.0)
assert_true(result["attack_started"])        # 不需要开窗口，不需要场景，毫秒级跑完
```

对比一下：如果状态机直接写在 `Player extends CharacterBody2D` 里，你想测"第 12 帧能不能取消接下一段"，就必须把整个游戏跑起来、把角色挪到敌人面前、精确在第 12 帧按键——**根本没法自动化**。

> **分工原则**：
> - **纯逻辑**（能不能取消、伤害怎么算、房间怎么生成）→ 写成 `RefCounted`，由 `tests/` 里的单元测试保证。
> - **接线**（节点路径对不对、信号连没连、依赖注入顺序）→ 写成薄薄的 `Node`，由 `smoke_run.tscn` 保证。
>
> 这两层加起来，才覆盖得住 AI 改代码带来的回归风险。**给 AI 派活时，能写成纯逻辑的就必须写成纯逻辑。**

#### 事件总线的样子（`scripts/core/event_bus.gd`，实际代码）

```gdscript
extends Node
# 全局广播站。注册方式：项目设置 → Autoload → 路径填 res://scripts/core/event_bus.gd，节点名填 EventBus

signal hit_confirmed(attack_id: String, hitstop_frames: int, shake: float, world_pos: Vector2)
signal player_damaged(amount: int, remaining_hp: int)
signal enemy_damaged(amount: int, remaining_hp: int, world_pos: Vector2)
signal attack_phase_changed(attack_id: String, phase: String, frame: int)
signal room_cleared(room_id: String)
```

```gdscript
# 判定盒命中时（在 hurtbox.gd 里）—— 只管喊一嗓子，不管谁来听
EventBus.hit_confirmed.emit(hitbox.attack_def.id, def.hitstop, def.shake, global_position)

# 打击感总控（在 combat_director.gd 里）—— 订阅：有人打中我就顿一下 + 抖一下
func _ready() -> void:
    EventBus.hit_confirmed.connect(_on_hit_confirmed)

func _on_hit_confirmed(_id: String, hitstop_frames: int, shake: float, _pos: Vector2) -> void:
    hitstop.request(hitstop_frames)
    self.shake.add(shake)
```

> **这套写法最大的好处**：以后加"命中音效""伤害数字""手柄震动"三个功能，只需要写三个新文件各自 `connect` 到 `hit_confirmed`，**完全不用改战斗代码**。AI 改的代码越少，改坏的概率越低。

#### 数据驱动的样子（`data/attacks.json`，实际数据）

```json
{
  "light_1": {
    "display_name": "轻击一段",
    "startup": 6,  "active": 3,  "recovery": 10,
    "cancel_from": 12,  "cancel_into": ["light_2"],
    "damage": 8,  "hitstop": 4,  "shake": 0.22,
    "knockback": 120.0,
    "hitbox_offset": [26.0, -20.0],  "hitbox_size": [40.0, 30.0]
  }
}
```

`startup / active / recovery` 就是格斗游戏里的**起手帧 / 判定帧 / 收招帧**，`cancel_from` 是"从第几帧起可以取消接下一招"。这三个数字直接决定手感，改它们**不用碰任何一行 GDScript**。

> **为什么用 JSON 而不是 Godot 的 `.tres` 资源？**
> `.tres` 在编辑器里点着改确实更舒服，但它是 Godot 私有格式，AI 写错时容易生成"看起来对、加载就崩"的文件，而且**在 diff 里不直观**。
> JSON 是通用格式：AI 写起来错误率低，你在 GitHub 上能直接看懂这次改了什么数值，还能写脚本批量校验。
> 代价是没有编辑器可视化——所以项目配了 `check` 调试命令来补这个短板（见阶段 3）。

#### 达标自测标准

- [ ] 我能画出"按键 → 状态切换 → 判定 → 掉血 → 特效/音效/震屏"的完整流程图，并标出每一步在哪个文件。
- [ ] 我能回答："我要把轻击一段的伤害从 8 改成 12，需要改代码吗？"（答案：不需要，改 `data/attacks.json`）
- [ ] 我能说清楚 `EventBus` 里每个 signal 分别是谁发、谁收。
- [ ] 我能说出为什么 `player_fsm.gd` 继承的是 `RefCounted` 而不是 `Node`，以及这样做换来了什么。
- [ ] 当 AI 说"我改好了"，我能定位到它到底改了哪几个文件。

### 阶段 3：验收能力（约 1 周，之后长期保持）

**目标**：把"感觉对不对"翻译成"可执行的验收用例"，让 AI 能自测、让你能复验。

**这是整个项目里最被低估、也最值钱的能力。** 会写验收用例的人，能把 AI 的产出从"看起来能跑"提升到"真的对"。

#### 要掌握的具体知识点

| 知识点 | 一句话解释 | 大概耗时 |
|---|---|---|
| 验收用例设计 | 一个功能写 3-7 条"输入 → 期望输出"，覆盖正常路径、边界、异常 | 3 小时 |
| 稳定复现 bug | 固定环境、固定步骤、固定随机种子；能录屏；能贴日志 | 2 小时 |
| 给 AI 写修改要求 | 一次只改一件事，说清"不要动什么"，给出可验证的完成标准 | 2 小时 |
| 看代码 diff | 在 GitHub 或 VS Code 里看 `+` / `-` 行，确认 AI 没有偷偷删掉别的功能 | 2 小时 |
| 自动化测试入门 | 知道 Godot 能 `--headless` 跑测试脚本；知道 GUT 这类测试插件的存在 | 1 小时 |

#### 验收用例长什么样（以"冲刺闪避"为例）

| # | 前置条件 | 操作 | 期望结果 |
|---|---|---|---|
| 1 | 站在地面，满血 | 按冲刺键 | 0.15 秒内进入 Dash 状态，速度达到 520 |
| 2 | 冲刺中 | 再次按冲刺键 | **不生效**（不能连冲） |
| 3 | 冲刺中 | 按攻击键 | **不生效**（冲刺不可取消） |
| 4 | 冲刺刚开始的 6 帧内 | 被敌人攻击命中 | **不掉血**（i-frames 生效） |
| 5 | 冲刺结束后的第 1 帧 | 被敌人攻击命中 | **正常掉血** |
| 6 | 冲刺中 | 撞到墙壁 | 速度归零，不穿墙，不卡在墙里 |
| 7 | 站在悬崖边 | 按冲刺键 | 冲出去后正常下落，不悬空 |
| 8 | 冲刺全程 | 观察 | 冲刺音效只播一次，不叠加 |

**8 条里有 4 条是"不该发生的事"**——初学者最容易漏掉的就是这类反向用例，而 AI 最容易写错的也正是这些。

#### 怎么让 AI 自己跑测试

Godot 支持无界面运行，可以让 AI 在改完代码后自己验证。**下面这些命令本仓库已经全部跑通**，可以直接抄给 AI：

```bash
# 本仓库的 Godot 在 .tooling/ 下（已被 .gitignore 排除，不进版本库）。
# 每个人自己下载一份，版本必须是 4.7.2，见 docs/01-工具清单.md。
GODOT=".tooling/Godot_v4.7.2-stable_win64_console.exe"

# 0) 新增了 .gd / .tscn 文件之后，必须先重新导入一次。
#    不跑这一步，脚本之间互相引用（class_name）会解析不到，报 "Could not find type"。
"$GODOT" --headless --path game --import

# 1) 单元测试：纯逻辑层（状态机 / 伤害公式 / 帧数据 / 房间生成 / 重放）
"$GODOT" --headless --path game --script res://tests/run_tests.gd
#    全部通过时进程返回 0，有失败返回 1 —— AI 可以自己看退出码

# 2) 冒烟测试：真的把游戏跑起来，自动玩 600 帧 + 站着挨打 + 检查调试台
"$GODOT" --headless --path game res://tests/smoke_run.tscn

# 3) 只做语法检查，不启动游戏（最快的"编译"检查，适合单文件小改）
"$GODOT" --headless --path game --check-only --script res://scripts/player/player_fsm.gd
```

> **这三条命令是整个验收流程的骨架**，详细用法见 [03-验收清单.md](03-验收清单.md)。
> 给 AI 的指令里可以直接写："改完后请自己运行第 1 条和第 2 条命令，把**完整输出**贴给我，不要只说'通过了'。"
>
> ⚠️ 注意 `--path game` 这个参数：它告诉 Godot"项目根目录是 `game/`"。
> 忘了写会报 "Error: Couldn't load project data at path"，这是新手最常踩的坑。
> 其余命令行参数以 [Godot 官方文档](https://docs.godotengine.org/) 为准。

#### 看 diff 的三个必查项

1. **有没有删掉不相关的行**（AI 经常会"顺手重构"，这是最大风险来源）。
2. **有没有硬编码数字**（看到 `if hp < 37:` 这种就要问为什么不是 `@export` 的变量）。
3. **有没有留下调试垃圾**（`print("here")`、被注释掉的大段旧代码）。

#### 达标自测标准

- [ ] 我能为一个新功能在 15 分钟内写出 5 条以上验收用例，其中至少 2 条是反向用例。
- [ ] 我能让队友照着我的 bug 描述 100% 复现问题，不需要我再解释。
- [ ] 我给 AI 提需求时，能明确写出"不要改动的文件/行为"。
- [ ] 我能看懂 diff，并在 5 分钟内判断"这次改动有没有引入风险"。
- [ ] 我知道一个功能做完后，应该用什么命令让 AI 自己先验一遍。

### 阶段 4：手感调优（约 2 周入门，之后贯穿整个项目）

**目标**：能说出"这一刀砍下去不爽"，并且知道该调哪个数字。

**这是本项目唯一 AI 帮不了你的部分。** AI 能写出 60 帧的攻击动画逻辑，但它不知道"这一刀该有多重"。手感是人的工作，也是这个项目真正的核心竞争力。

#### 要掌握的具体知识点

| 知识点 | 一句话解释 | 大概耗时 |
|---|---|---|
| 帧数据（起手 / 判定 / 收招） | 一次攻击分三段：起手帧（按下到生效，决定"重不重"）、判定帧（能打中人的窗口）、收招帧（不能动的时间，决定"风险多大"） | 3 小时 |
| 顿帧 hitstop | 命中瞬间把时间几乎冻住几帧，让打击"实"。通常是 2-8 帧 | 2 小时 |
| 屏幕震动 | 相机随机偏移。关键是**幅度小、衰减快**，大震动只留给重击和 Boss | 1 小时 |
| 输入缓冲 input buffer | 提前几帧按键也算数（通常 6-10 帧）。没有它，玩家会觉得"我明明按了" | 2 小时 |
| 无敌帧 i-frames | 受击/闪避后短暂无敌。通常闪避 6-12 帧，受击后 20-40 帧 | 2 小时 |
| 打击音效时机 | 音效要**和判定帧同帧**播放，并做 ±5% 随机音高，否则连续攻击会"机关枪" | 1 小时 |
| 取消窗口 cancel window | 收招的后半段允许被下一段攻击取消，这是连招流畅度的关键 | 2 小时 |
| 手感的调试方法 | 固定帧率录屏 → 逐帧看 → 记录数字 → 改一个变量 → 再录 → 对比 | 3 小时 |

#### 一套可直接照抄的起始数值（横版动作游戏）

| 动作 | 起手帧 | 判定帧 | 收招帧 | 顿帧 | 说明 |
|---|---|---|---|---|---|
| 轻击 1 | 5 | 3 | 8 | 2 | 快，能连 |
| 轻击 2 | 6 | 3 | 10 | 3 | 稍慢，位移略大 |
| 轻击 3 | 9 | 4 | 16 | 5 | 收尾，击退强 |
| 重击 | 14 | 5 | 24 | 6 | 慢、疼、风险高 |
| 闪避 | — | 无敌 8 帧 | 8 | — | 无敌帧在起手就生效 |

> 60 FPS 下，1 帧 ≈ 16.7 毫秒。上表的"轻击 1"从按下到打中约 83 毫秒——这是玩家感觉"跟手"的量级。

> ⚠️ **别把上表当成本项目的实际数值。** 它是为了让你看懂"起手/判定/收招/顿帧这四个数怎么互相配合"
> 而给的一组**示意值**。本项目真正在跑的是 [`game/data/attacks.json`](../game/data/attacks.json)：
>
> | 招式 | 起手 | 判定 | 收招 | 顿帧 | 备注 |
> |---|---|---|---|---|---|
> | `light_1` 轻击·一段 | 6 | 3 | 10 | 4 | 可取消接 `light_2` |
> | `light_2` 轻击·二段 | 5 | 3 | 11 | 5 | 比一段更快，制造"连段加速"感 |
> | `light_3` 轻击·三段 | 8 | 4 | 18 | 8 | 收尾，不可取消，击退 220 |
> | `heavy_1` 重击·力劈 | 14 | 5 | 22 | 9 | 高风险高回报，不可取消 |
> | `enemy_swipe` 山贼·横砍 | 16 | 4 | 18 | 5 | 敌人招式，起手很慢，给玩家反应时间 |
>
> **验收手感时一律以 `attacks.json` 为准。** 想知道"这一招到底几帧"，用调试台 `data light_1` 直接打出来，
> 比翻文档可靠——文档会过期，数据表不会。

#### 关键实现要点（读得懂就行，代码让 AI 写）

**顿帧（hitstop）**：全局减速几帧再恢复。注意计时器必须**忽略时间缩放**，否则永远恢复不了。

```gdscript
func hitstop(frames: int) -> void:
    Engine.time_scale = 0.05
    # 第 4 个参数 ignore_time_scale = true 是关键，否则计时器自己也变慢了
    await get_tree().create_timer(frames / 60.0, true, false, true).timeout
    Engine.time_scale = 1.0
```

**输入缓冲（input buffer）**：记住"最近 N 帧内按过什么键"。

```gdscript
var buffered_attack_frames: int = 0

func _physics_process(_delta: float) -> void:
    if Input.is_action_just_pressed("attack"):
        buffered_attack_frames = 8          # 记住 8 帧
    elif buffered_attack_frames > 0:
        buffered_attack_frames -= 1

    # 收招快结束时，如果缓冲区里还有攻击输入，就接下一段
    if state == State.RECOVERY and buffered_attack_frames > 0:
        _start_next_attack()
        buffered_attack_frames = 0
```

**无敌帧（i-frames）**：用一个布尔量挡住伤害入口，比改碰撞层更不容易出 bug。

```gdscript
var invincible_frames: int = 0

func take_damage(amount: int) -> void:
    if invincible_frames > 0:
        return                       # 无敌中，直接忽略
    hp -= amount
    invincible_frames = 30
    EventBus.player_damaged.emit(amount, hp)
```

**屏幕震动**：幅度要小，衰减要快。

```gdscript
func shake(strength: float) -> void:
    var t := create_tween()
    for i in 4:
        t.tween_property(self, "offset",
            Vector2(randf_range(-1, 1), randf_range(-1, 1)) * strength, 0.03)
        strength *= 0.6              # 每一跳衰减到 60%
    t.tween_property(self, "offset", Vector2.ZERO, 0.05)
```

#### 达标自测标准

- [ ] 我能用"起手 8 帧、判定 4 帧、收招 12 帧"这种句式描述一个动作，而不是"感觉有点慢"。
- [ ] 我能独立把轻击的手感从"飘"调到"实"（至少用上顿帧 + 震屏 + 音效三件套）。
- [ ] 我知道"玩家说按了没反应"时，第一个该检查的是输入缓冲。
- [ ] 我能说出为什么受击后要给 i-frames，以及给太长会有什么问题（变成无脑莽）。
- [ ] 我能通过逐帧看录屏，定位到"判定帧比动画早了 2 帧"这类具体问题。

### 3.1 通用模板（复制这段）

```markdown

  手感数值集中在 res://scripts/core/game_config.gd，禁止散落硬编码

1. 冲刺开始的 8 个物理帧内免疫伤害
2. 冲刺结束后有 12 帧冷却，冷却期间按冲刺键无效
3. 无敌期间角色贴图每 2 帧闪烁一次（用 modulate.a 在 0.3 和 1.0 之间切）
4. 冲刺音效只播一次

## 约束
- 只允许修改：player_fsm.gd、player.gd
- 冲刺的状态切换逻辑必须写在 PlayerFsm 里（纯逻辑、可单测），
  player.gd 只负责调用状态机 + move_and_slide，不要把判断塞进节点层
- 不要动 event_bus.gd、hurtbox.gd，不要改任何 .tscn 场景文件
- 所有数值（8 帧、12 帧）必须写进 game_config.gd 并给出默认值
- 不要重构无关代码，不要改缩进风格（本项目统一 4 空格），不要加新的 autoload
- 不要引入任何第三方插件

## 验收标准
1. 冲刺中被打中，血量不变；冲刺结束后第 1 帧被打中，正常掉血
2. 连续快速按冲刺键，两次冲刺之间的间隔不少于 12 帧
3. 冲刺过程中反复按冲刺键，不会出现速度叠加或动画卡死
4. 贴图闪烁在无敌结束后立即恢复为完全不透明（modulate.a == 1.0）
5. 请在 tests/test_player_fsm.gd 里补上对应单元测试，**至少包含 2 条反向用例**
   （例如"冷却期间按冲刺不生效""第 9 帧被打中应该掉血"）
6. 改完后请自己运行，并把**完整输出**贴给我，不要只说"通过了"：
   godot --headless --path game --script res://tests/run_tests.gd
   godot --headless --path game res://tests/smoke_run.tscn
7. 请列出你改动的每一处，以及为什么改，我要逐条核对
```

## 4. 常见误区

### 误区 1：一开始就做完整系统

**错在哪**：第一周就想把"状态机 + 事件总线 + 数据驱动 + 存档 + 肉鸽地图生成 + 祝福系统"全搭起来。结果每个系统都是半成品，谁也跑不起来，AI 每次改都在一个 3000 行的烂摊子上打补丁，错误率爆炸。

**正确做法**：**第 1-2 周只做一件事——一个方块人能跑、能跳、能砍中一个不会动的木桩。** 手感对了再加第二个系统。原则是"**每个周末都必须有一个能跑起来给人玩的版本**"，哪怕它只有 1 个房间 1 种敌人。

---

### 误区 2：不写验收用例，靠"我玩一下看看"

**错在哪**：玩一下只能发现"明显坏了"，发现不了"冲刺第 7 帧被打中会同时触发受击和无敌"这种边界问题。等问题积累到 20 个，你根本分不清是哪个功能坏了。

**正确做法**：每个功能合并前，在 PR 描述里贴一张验收用例表（见阶段 3 的 8 条示例）。**没写用例的功能不算做完**，只算"写完了"。另外让 AI 用 `godot --headless --script` 自己跑一遍断言。

---

### 误区 3：让 AI 一次改太多

**错在哪**："帮我实现完整的战斗系统，包括连招、格挡、弹反、处决、武器切换。" AI 会给你 800 行代码，你既看不懂也没法验收；一旦有 bug，你连是哪部分坏的都不知道。**一次改动的规模超过 200 行或 5 个文件，你的验收能力就归零了。**

**正确做法**：**一次一个功能，一次不超过 2-3 个文件。** 用阶段 3 的模板，在"约束"里明确写"只允许修改 X 和 Y"。宁可提 6 次需求做连招，也不要提 1 次需求做 6 个连招。

---

### 误区 4：不读代码，只把报错贴给 AI

**错在哪**：报错信息只说"第 42 行空指针"，不说"为什么会空"。你把报错丢过去，AI 就会猜，猜错一次你就再贴一次，来回 10 轮，时间和额度全烧光，最后 AI 可能把本来对的地方也改坏了。

**正确做法**：贴报错的同时，**自己先读一遍那 20 行代码**，说出你的判断（哪怕判断是错的）。参考阶段 3 的 bug 模板最后一段。你会读代码，AI 的修复成功率会翻倍；你不会读，就只是在一遍遍抽奖。

---

### 误区 5：美术先行

**错在哪**：前两个月都在画角色八方向行走图、做 UI 皮肤、设计 40 种武器图标。等到真的要写战斗逻辑时，发现角色尺寸和判定盒对不上、动画帧数和手感数值冲突、40 个图标只用了 3 个。**美术资产在玩法定型前基本都是要重做的。**

**正确做法**：**前 6 周全部用色块和免费占位素材。** 角色就是一个 32×32 的红色方块，敌人是蓝色方块，武器是白色矩形。玩法定型后（能连打 3 段、手感自己满意），再花 1-2 周集中替换美术。像素素材先买/下载免费的（Kenney、itch.io 上 CC0 的包），别自己画。

---

### 误区 6：忽略手感，觉得"功能做完了就行"

**错在哪**：功能清单打勾 100%，但角色跳起来像纸片、打中敌人没反馈、按了键要等 300 毫秒才动。**横版动作游戏 90% 的成败在手感，不在功能数量。** 《死亡细胞》和一堆同类游戏的功能几乎一样，差别全在帧数据和反馈上。

**正确做法**：把阶段 4 的八个知识点当成**第一优先级需求**，而不是"以后优化"。判定标准很简单：**让一个没玩过的人玩 30 秒，问他"爽不爽"。** 他说"有点飘""打上去没感觉"，就停下来调手感，不要再加新功能。

---

### 误区 7：把 AI 当编译器用，不做版本控制

**错在哪**：AI 改了 15 个文件，你直接覆盖本地代码，跑不起来了，想退回上一个版本——发现上次 commit 是 5 天前。**AI 协作模式下，代码的变动速度是手写的 5-10 倍，没有 Git 就是在裸奔。**

**正确做法**：**每次让 AI 动手之前先 commit 一次**（哪怕只是 `wip: 准备加冲刺无敌`）。AI 改完验证通过再 commit 一次。一个功能一个 commit，一个功能一个分支。出问题就 `git reset --hard` 或 `git revert`，两秒钟回到能跑的状态。

---

### 误区 8：四个人都在改同一批文件

**错在哪**：程序、美术、策划三个人同时改 `player.gd` 和 `Game.tscn`，每天都在解决冲突，冲突解决错了还引入了看不见的 bug。

**正确做法**：**按文件/目录划分所有权。** 谁负责战斗就独占 `game/scripts/combat/`，谁负责角色就独占 `game/scripts/player/`，谁负责关卡就独占 `game/scripts/world/` + `game/data/rooms.json`。场景文件 `.tscn` 的冲突极难解决，所以**规定只有一个人能在 Godot 编辑器里改 `scenes/`**，其他人要改场景必须先说。另外把"手感数值"全部提取到 `data/*.json` 和 `game_config.gd` 里，这样调数值完全不碰逻辑代码，冲突概率降到接近 0。

## 5. 每周节奏建议

### 5.1 核心比例

| 项目阶段 | 让 AI 写 | 自己验 + 调 | 说明 |
|---|---|---|---|
| 第 1-3 周（学阶段 0-1） | 60% | 40% | 让 AI 写小 demo，你主要在做阅读练习 |
| 第 4-8 周（做核心玩法） | 40% | 60% | 写只是开始，验收和调手感才是主要工作量 |
| 第 9 周以后（加内容） | 30% | 70% | AI 写一个敌人只要 20 分钟，验收加调手感要 2 小时 |

**一句话**：**AI 越快，你的验收时间就越长。** 不要因为"AI 一分钟就写完了"就跳过验收。

### 5.2 一周的固定节奏（按每人每周 10 小时设计）

| 时间 | 时长 | 做什么 | 谁参与 |
|---|---|---|---|
| 周一晚 | 1 小时 | **定需求**：把本周要做的 2-3 个功能写成验收用例，开好 issue | 全员（30 分钟足够，别开会超过 1 小时） |
| 周二晚 | 2 小时 | **让 AI 写**第 1 个功能 + 你逐行读 diff，看不懂就问 AI"这一行在干什么" | 主程 + 1 人旁读 |
| 周三晚 | 2 小时 | **让 AI 写**第 2 个功能；同时**手工搭场景**（美术/策划在 Godot 编辑器里干活） | 分工并行 |
| 周四晚 | 1 小时 | **自查**：跑 headless 检查，看有没有报错；跑验收用例，记录失败项 | 主程 |
| 周五晚 | 1 小时 | **修 bug**：把周四发现的问题整理成 bug issue，一条一条喂给 AI | 主程 |
| 周六下午 | 2 小时 | **手感调优**：只用游戏手柄/键盘玩，逐帧看录屏，调 `data/attacks.json` 和 `game_config.gd` 里的数值 | 全员一起玩，一起说感受 |
| 周日晚 | 1 小时 | **收尾**：合并分支、打 tag、写一句"本周变化"、更新下周 issue | 主程 |

### 5.3 三条硬性时间纪律

1. **每天不超过 1 小时连续"读 AI 代码"**。超过 1 小时注意力会掉，你会开始"看不懂也点通过"——这是项目质量崩塌的起点。
2. **周五之前必须有一个能跑起来的版本**。哪怕功能没做完，也要保证主干能运行。**永远不要把"跑不起来"的状态留到周末。**
3. **每周至少留 2 小时纯粹玩自己的游戏**，不做任何开发。不玩就不知道手感差在哪，也不知道下周该做什么。

### 5.4 每周复盘要回答的 4 个问题（10 分钟，写进 issue）

1. 本周哪个功能"AI 写完我以为对了，结果验收时发现错了"？为什么会漏掉？
2. 本周哪次给 AI 的需求一次就对了？把那段提示词存下来，以后复用。
3. 哪个数值是我调了 3 次以上还没调对的？下周优先解决它。
4. 本周有没有"为了赶进度跳过验收"的情况？如果有，这周补上。

## 附录 A：读代码常用的术语对照表

| 英文 | 中文 | 你只需要知道 |
|---|---|---|
| Node | 节点 | Godot 里一切东西的基本单位 |
| Scene | 场景 | 一个可复用的节点树，存成 `.tscn` |
| Script | 脚本 | 挂在节点上的 `.gd` 文件 |
| Signal | 信号 | 节点间的广播，`emit()` 发，`connect()` 收 |
| `_ready()` | 就绪回调 | 节点进入场景时跑一次，做初始化 |
| `_process(delta)` | 每帧回调 | 每个渲染帧跑一次，用于视觉表现 |
| `_physics_process(delta)` | 物理帧回调 | 固定 60 次/秒，**判定和移动写这里** |
| `delta` | 时间增量 | 上一次到这一次过了多少秒，做时间相关的计算要乘它 |
| `@export` | 导出变量 | 让变量显示在编辑器面板，不用改代码就能调 |
| `@onready` | 延迟初始化 | 等节点树就绪后再取子节点引用 |
| Autoload | 自动加载单例 | 全局唯一的节点，事件总线就靠它 |
| Resource | 资源 | 可复用的数据对象，存成 `.tres`（本项目用 JSON 代替，见阶段 2） |
| Hitbox / Hurtbox | 攻击盒 / 受击盒 | 打人的区域 / 挨打的区域 |
| Hitstop | 顿帧 | 命中瞬间冻结几帧，打击感来源 |
| i-frames | 无敌帧 | 一段时间内免疫伤害 |
| Input Buffer | 输入缓冲 | 提前几帧按键也算数 |
| Startup / Active / Recovery | 起手 / 判定 / 收招 | 一次攻击的三个阶段 |
